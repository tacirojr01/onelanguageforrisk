Appendix C

Open formats: records that can leave the building

Most of the twenty-seven sources are prose: principles and steps that each organisation translates into its own fields, differently. Four publish a format a program can check. This page explains what that means for a risk professional, and then offers the files.

What a schema is, in plain words

A schema is the list of fields a record must have, with the type of each (a date, a number, one of a fixed set of values) and the rules they obey. When two organisations adopt the same idea, each designs its own table, and the two cannot be joined without a mapping that someone writes, maintains and gets wrong. When they adopt the same format, there is nothing to map: a record can leave the organisation, to a supervisor, an insurer, a parent or an auditor, and arrive meaning the same thing. A validator is a program that checks a record against the schema and says whether it conforms, so the check is run by software rather than argued in a meeting.

The files below are written in JSON, a plain-text format for structured data that any program can read: a record is a list of named fields and their values. Despite the name, it has nothing to do with programming in JavaScript; it is simply the common language for exchanging data between systems, the way PDF is for documents.

The five the framework proposes

No open schema exists for an objective, a control, a scenario, an indicator or an assurance activity: the things an organisation does about risk rather than what happens to it. The framework publishes draft schemas for the five, shaped like the four that exist, with the attributes of Table 19.1 of the book. They stay proposals until someone other than the author has used them in a running register; if you have, tell us.

A worked example, read field by field

This is the payments risk of chapters 17 and 18 of the book, PAY-014, as a register row with the framework's extensions. The first block is the published NIST row: identifier, the validated statement as description, category, likelihood, impact, exposure, response, cost, owner and status. The crmf block carries what the framework adds: the statement broken into its four parts, the taxonomy node, the tier, the consequence against each objective, the precision of the likelihood, the three snapshots of exposure (inherent, expected, measured), the actual cost of the response, the named decider, the Action Priority band, and the versions the row was scored under.
